# Exporter Plugin SDK

Guide for adding and maintaining code generators that consume **ExportIR** and emit downloadable source files.

**Related:** [Export Pipeline](./04-export-pipeline.md) · [Architecture — Extensibility](./02-architecture.md#extensibility) · [Local Development & Components](./13-local-development-and-components.md)

---

## Overview

RosettaDash exporters are **pure functions** (today) that transform validated `ExportIR` into an array of `GeneratedFile` entries. The builder never parses raw canvas JSON inside exporters — IR is the only input.

```
Composite  →  validate  →  buildExportIR()  →  ExporterPlugin.generate()  →  GeneratedFile[]
```

Built-in plugins are listed in `@rosettadash/core`:

```typescript
import { builtInExporterManifest } from '@rosettadash/core';
```

Source: `packages/core/src/lib/export/exporter-manifest.ts`

The NestJS orchestrator (`apps/server/src/app/export/export.service.ts`) imports each `generate*Files` function and dispatches by target. A dynamic loader may replace hard-coded imports later; the **plugin contract** stays the same.

---

## Plugin contract

Defined in `packages/core/src/lib/export/exporter-plugin.ts`:

| Type | Purpose |
|------|---------|
| `GeneratedFile` | `{ path, content, encoding: 'utf-8', description? }` |
| `ExportOptions` | Optional `{ rootDir? }` for UI bundles |
| `ExporterGenerateFn` | `(ir: ExportIR, options?) => GeneratedFile[]` |
| `ExporterPlugin` | Full runtime registration including `generate` |
| `ExporterPluginDescriptor` | Metadata-only entry (manifest, docs, tests) |

Minimal plugin shape:

```typescript
import type { ExportIR, ExporterPlugin, GeneratedFile } from '@rosettadash/core';

export const solidUiExporter: ExporterPlugin = {
  id: 'ui.solid',
  label: 'Solid UI',
  targetKind: 'ui',
  supportedTargets: ['solid'],
  packageName: '@rosettadash/exporters-solid',
  entryExport: 'generateSolidUiFiles',
  generate(ir: ExportIR): GeneratedFile[] {
    if (ir.targets.ui !== 'solid') {
      throw new Error('Solid exporter requires ui target "solid"');
    }
    return [
      {
        path: 'src/Dashboard.tsx',
        content: '// generated Solid dashboard',
        encoding: 'utf-8',
        description: 'Solid dashboard entry',
      },
    ];
  },
};
```

## Adding a new UI exporter

Follow the pattern in `packages/exporters-react`:

### 1. Scaffold package

```
packages/exporters-solid/
├── package.json          # name: @rosettadash/exporters-solid
├── project.json          # Nx library + test/lint targets
├── src/
│   ├── index.ts          # export generateSolidUiFiles
│   └── lib/
│       ├── types.ts        # GeneratedFile (or import from core later)
│       ├── utils.ts        # naming, string helpers
│       ├── component-templates.ts  # per IRComponent.type templates
│       ├── binding-resolver.ts     # optional wiring helpers
│       └── generate-solid-ui.ts
```

Add the package to root `tsconfig` paths and `apps/server` dependencies.

### 2. Implement `generate*Files(ir)`

Checklist for a UI exporter:

- [ ] Guard `ir.targets.ui` matches your framework
- [ ] Iterate `ir.components` — emit one file per visual component
- [ ] Emit shared `types.ts` and `styles/tokens.css` from `ir.styles` / env vars
- [ ] Handle `ir.dataSources` stubs referenced by components (PostgreSQL pool, etc.)
- [ ] Respect `ir.meta.exportScope` / `exportNodeIds` when present (partial export)
- [ ] Map `ir.events` bindings into props or hooks in generated components
- [ ] Apply `ir.domain` role visibility when components expose `visibilityRoles`

Reference implementation: `packages/exporters-react/src/lib/generate-react-ui.ts`

### 3. Component templates

Each registry type used in exports needs a template branch:

```typescript
// component-templates.ts (conceptual)
export function generateComponentFile(component: IRComponent, exportName: string): string {
  switch (component.type) {
    case 'visual.table':
      return generateTableComponent(component, exportName);
    case 'visual.chart.line':
      return generateLineChartComponent(component, exportName);
    default:
      throw new Error(`Unsupported component type: ${component.type}`);
  }
}
```

When adding a **new component type** to the palette, update **all** UI exporters (or accept matrix test failures).

### 4. Register the plugin

1. Append descriptor to `builtInExporterManifest` in core
2. Import generator in `apps/server/src/app/export/export.service.ts`
3. Add `case` in `generateUiFiles` switch (or future registry dispatch)
4. Extend export wizard target picker in the Angular client
5. Add matrix fixture + spec in `export-target-matrix.fixtures.ts`

### 5. Test

```bash
npx nx test exporters-solid
npx nx test server   # export target matrix
npm run verify
```

Minimum tests:

- Generates entry dashboard file for a small IR fixture
- Throws when `ir.targets.ui` mismatches
- Covers at least one binding-heavy component (table + filter)

## Adding a server or database exporter

Server exporters (`packages/exporters-nest`, etc.) focus on:

- `ir.dataSources` with types `infra.server.*` and database nodes
- `ir.routes` HTTP handlers
- Env var specs → `.env.example` snippets
- Auth / role guard stubs (`x-rosettadash-role` pattern)

Database **layer** exporters (MongoDB, Supabase, MySQL) emit client modules under `database/src/`. They run **instead of** generic server DB wiring when the user picks a database target in the export wizard.

See `packages/exporters-nest/src/lib/generate-nest-infra.ts` for the most complete reference.

## ExportIR fields exporters rely on

| Field | Used for |
|-------|----------|
| `meta` | Names, version stamp, export scope |
| `targets` | Which plugins to invoke |
| `components` | UI component files |
| `layouts` | Layout wrapper components |
| `dataSources` | DB pools, server modules |
| `routes` | API route files |
| `events` | Wiring between components |
| `envVars` | `.env.example` generation |
| `domain` | Client/project context, default filters, roles |

Build IR with:

```typescript
import { buildExportIR, defaultComponentRegistry } from '@rosettadash/core';

const ir = buildExportIR(composite, defaultComponentRegistry, {
  exportScope: 'full',
});
```

Never read `composite.nodes` directly inside an exporter.

## Output conventions

| Kind | Typical paths |
|------|----------------|
| UI | `src/components/*.tsx`, `src/Dashboard.tsx`, `src/styles/tokens.css` |
| Server | `server/src/main.ts`, `server/src/modules/*` |
| Database layer | `database/src/*.client.ts` |

All exports include UTF-8 text. Binary assets are out of scope for Phase 7.

File paths must be **stable** across regenerations (no random suffixes) so users can diff exports.

## Orchestration today vs future

| Today | Future |
|-------|--------|
| Hard-coded imports in `ExportService` | Registry resolves `ExporterPlugin` by `targets` |
| Manifest is metadata + docs | Manifest loads plugins dynamically (npm packages) |
| Wizard lists static target enums | Wizard reads `builtInExporterManifest` |

Third-party plugins should still implement the same `ExporterPlugin` interface and publish an npm package. Registration will move from manual switch statements to manifest-driven loading without changing generator function signatures.
